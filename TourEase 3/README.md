# TourEase — Smart Tourist Guide (iOS / SwiftUI)

Premium travel-planning app. Delivered in 4 phases per the spec. This drop is **Phase 1**.

## Phase Plan
- **Phase 1 (this drop):** Folder structure, app architecture, full authentication flow (email, Google, Apple, sign up, forgot password, remember me, validation, loading/error states, ad banner slot on login).
- **Phase 2:** Home dashboard, route planner, transport comparison.
- **Phase 3:** Budget calculator, hotels, food, history.
- **Phase 4:** Admin portal, ad management, persistence polish, final integration.

Say "continue with Phase 2" and I'll build the next module the same way, wired into what's here.

## Tech Stack
- Swift 6, SwiftUI, MVVM
- SwiftData (local persistence — history, saved trips, session flag)
- Firebase Auth + Firestore (auth + admin/ad data) — behind a protocol so the app compiles and runs with a **mock service** even before you wire Firebase, so you can demo it today and swap in real Firebase in 5 minutes.
- async/await throughout, no completion-handler soup.

## How to run in Xcode
1. Create a new iOS App project in Xcode ("TourEase"), Interface: SwiftUI, Language: Swift, and make sure "Use SwiftData" is checked (or add SwiftData manually — it's built into iOS 17+/Swift 6 toolchains).
2. Delete the default `ContentView.swift`/`TourEaseApp.swift` Xcode generates.
3. Drag every file/folder from this package into the Xcode project navigator (check "Copy items if needed", add to target "TourEase").
4. **Firebase (optional for now):** the app runs fully today using `MockAuthService` — email/Google/Apple buttons all work with simulated network delay so you can demo without any backend. To go live: add the Firebase iOS SDK via Swift Package Manager (`https://github.com/firebase/firebase-ios-sdk`), drop your `GoogleService-Info.plist` into the project, then in `TourEaseApp.swift` flip `useMockAuth` to `false` and uncomment the `FirebaseAuthService` calls (marked `// FIREBASE:` throughout).
5. Build & run on iOS 17+ simulator (iPhone 15 Pro recommended for the UI proportions used).
6. **Route Planner (Module 2) needs one manual Info.plist entry** — Xcode won't let CoreLocation prompt for permission without it: Project Navigator → Info.plist (or Target → Info tab) → add key `NSLocationWhenInUseUsageDescription` → value `"TourEase uses your location to plan routes and find nearby places."` Everything else in this module is pure code, no other setup needed. On Simulator, use Features → Location → Custom Location (or "Apple") to get a usable current-location fix.
7. **Weather (Module 8) needs the WeatherKit capability**, which requires a **paid Apple Developer Program account** — WeatherKit isn't available on the free tier. Project → Target → Signing & Capabilities → "+ Capability" → WeatherKit. Without this, the screen still works: it automatically falls back to clearly-labeled sample data (a visible banner says so) instead of crashing or silently showing fake numbers as live.
8. **Ad banner images (Module 12) need `https` URLs** — iOS's App Transport Security blocks plain `http` image loads by default. When uploading a banner from the Admin Portal, use an `https://` image URL (any public HTTPS image works for a demo). A banner with no image URL, or one that fails to load, still shows correctly as a text-only banner rather than breaking the layout.

## Build Log (updates as modules land)
- **Module 1 — Home Dashboard:** 12 animated cards, role-based routing preserved, `Emergency` and `Profile` built out fully, everything else routes through `ComingSoonView` until its module lands.
- **Module 2 — Route Planner:** Source/destination autocomplete (`MKLocalSearchCompleter`), "use current location" (`CoreLocation`), real route calculation + polyline via `MKDirections` (no mock — this is a genuine Apple API), live `Map` with route overlay, travel summary card (distance, ETA, days, people).
- **Module 3 — Transport Comparison:** 8-mode comparison (Car, Bus, Train, Flight, Taxi, Auto, Bike, Walking). Car/Walking use real `MKDirections` routes; Taxi/Auto/Bus/Train/Flight use a documented `TransportPricingProviding` mock (clearly labeled "Estimated" in the UI, never shown as live) — swap for a real backend later without touching the view. Sort by Cheapest/Fastest/Balanced, single "Recommended" badge, availability/traffic chips per mode.
- **Module 4 — Smart Budget Planner:** Trip days, hotel category, food preference, taxi/auto/metro usage, shopping/activities sliders, emergency buffer — all live-recalculated (no button needed, calculation is pure). Native Swift Charts `SectorMark` pie chart with a total in the center, breakdown rows with % share, and **Save Budget** persisted locally via a new SwiftData model (`BudgetRecord`, registered in `TourEaseApp.swift`'s `ModelContainer`) so the History module can list it later without touching this one. Pricing lives behind `BudgetPricingProviding`, same swappable-mock pattern as transport.
- **Module 5 — Hotels:** Real MapKit POI search (`MKPointOfInterestFilter(including: [.hotel])`) around a resolved destination gives genuine hotel names/addresses/coordinates/distances; price tier and rating (which Apple's free search doesn't expose) come from a deterministic `HotelEstimating` layer, reusing Module 4's hotel-rate table, and are labeled "Estimated" on every card. Filter by category (reuses `PillSegmentedControl`), name search, sort by Price/Rating/Nearest, and **Save Favourite** persisted via a new SwiftData model (`FavoriteHotel`, added to the `ModelContainer`).
- **Module 6 — Food:** Always-visible Cost Averages grid (Breakfast/Lunch/Dinner/Street Food/Restaurant/Cafe) plus computed Daily Average (breakfast+lunch+dinner) and Weekly Average — all from a documented `FoodPricingProviding` mock. Below that, a real MapKit search (`.restaurant` + `.cafe` POI categories) for actual nearby places, each estimated-cost-labeled. No new SwiftData model this module — nothing here needs saving yet.
- **Module 7 — Nearby Places:** All 9 categories (Attractions, Museums, Parks, Restaurants, Hospitals, Police, ATMs, Petrol Pumps, Hotels) map to real `MKPointOfInterestFilter` categories — **the only module with zero mock data**, everything shown is genuine live MapKit search. New `NearbyCategoryChipRow` component (horizontally scrolling, for option sets too large for `PillSegmentedControl`'s fixed-width layout). Reuses `LocationManager` from Module 2 for "use current location."
- **Module 8 — Weather:** Real weather via Apple's **WeatherKit** (`AppleWeatherService`) — temperature, feels-like, humidity, rain chance, wind, sunrise/sunset, plus a rule-based "Weather Advice" line derived from those real numbers. Requires the WeatherKit capability + a paid Apple Developer account (Xcode step above); when unavailable, falls back automatically to `SampleWeatherService` with a visible "sample data" banner rather than crashing or faking live numbers.
- **Module 9 — Trip History:** Five tabs — Routes, Budgets, Hotels, Searches, Preferences. Routes/Budgets/Hotels/Searches read live from SwiftData (`RecentRouteRecord`, `BudgetRecord` from Module 4, `FavoriteHotel` from Module 5, `SearchHistoryRecord`); Preferences edits a single `UserPreferencesRecord`. Required small additive hooks in 5 already-built screens (Route Planner, Hotels, Food, Nearby Places, Weather) — one `.onChange`/button-tap call each to `SearchHistoryLogger` or a direct `modelContext.insert`, no ViewModel logic touched. "Saved Trips" and "History" dashboard cards both open this screen (a calculated route already is a trip record — a separate "Trips" model would just duplicate `RecentRouteRecord`).
- **Module 10 — Profile:** Real photo picker via **PhotosUI's `PhotosPicker`** (no Info.plist entry needed — it's out-of-process, one of the reasons Apple recommends it over the old image picker), editable display name, real-time Trips Completed / Saved Places counts (from Module 9's `RecentRouteRecord`/Module 5's `FavoriteHotel`), a Settings screen (notifications toggle, "Clear Local Data" with confirmation, real app version from `Bundle.main`), and Logout. All customization persisted locally via a new `UserProfileRecord`, keyed by user id so it survives logout/login. **Supersedes** Module 1's temporary `ProfileQuickView` stub (which explicitly said "full Profile module lands in its own pass") — that private struct was removed from `DashboardView.swift` entirely rather than left dead.
- **Module 11 — Admin Portal:** Same login, role-routed — no separate admin entry point (sign in with any email containing "admin"). **Manage Users**: suspend/delete against a locally-seeded demo directory (`AppUserRecord`), clearly labeled as a stand-in for a future Firestore `users` collection query (the exact real call is already commented into `FirebaseAuthService.fetchOrCreateUserDoc`). **Manage Ads**: upload/delete/schedule banners — reuses the `AdBanner` model that's existed since Phase 1 for the login screen's ad slot, so uploads here immediately affect what rotates on Login. **Manage Hotel/Food/Transport Pricing**: introduced `PricingOverridesStore` (`UserDefaults`-backed, since the pricing-provider structs are constructed as default parameters before any `ModelContext` exists) — edits here take effect **instantly** in the Hotels, Budget Planner, Food, and Transport Comparison modules, via one-line default-parameter swaps in 4 already-built files (`= DefaultXProvider()` → `= PersistedXProvider()`, same fallback values when nothing's overridden). **Analytics**: real `@Query` counts (routes planned, budgets saved, favorites, directory users, searches by module) — no fabricated platform-wide numbers, honestly scoped to "this device" until a backend exists. Replaces `RootView`'s temporary `AdminPortalPlaceholderView`, deleted outright.
- **Module 12 — Advertisement System:** Completed the ad pipeline Phase 1 only stubbed visually. `AdBannerImageCache` — real `URLSession` fetch, written to disk on success, so a previously-seen banner still renders **offline** (the "offline fallback cache" requirement) instead of showing a broken image. `AdBannerSlot` (Phase 1 component) now actually loads and displays each banner's image instead of title-only text. `LoginView` now queries real, currently-running `AdBanner` records (`#Predicate` + date filtering) instead of always passing an empty array — this was the actual gap: the login screen never had a real data source wired to it until now, so nothing admin uploaded could ever have shown up. No auth logic touched — only the ad-slot data source at the top of the screen.
- **Modules 13–15 — Final Polish:** Ran a real audit rather than a checkbox pass. **Part 13 (Local Storage): already complete** — the 9 `@Model` types built across earlier modules already cover Session, Trips/Routes, History, Budget, Settings, Favorites, Profile Images, and Ad Cache; nothing was missing. **Part 14 (Animations): two genuine gaps found and fixed** — `matchedGeometryEffect` was used nowhere in the app (added a sliding selection pill to `PillSegmentedControl`, `NearbyCategoryChipRow`, Transport Comparison's sort control, and History's tab row); Loading Skeletons/Shimmer Effects didn't exist (new `Components/ShimmerLoading.swift`, swapped in on Hotels/Food/Transport Comparison/Nearby Places/Weather in place of bare `ProgressView()` spinners). Also swapped plain `VStack` for `LazyVStack` on every dynamic-length result list (Hotels, Food, Nearby Places, Transport Comparison, History) — a real, if modest, performance improvement for longer lists. **Part 15 (Quality): one real gap found and partially fixed** — zero `accessibilityLabel`s existed anywhere; added them to every icon-only interactive control found (password visibility toggle, favorite heart, "use current location," profile photo picker, admin user-actions menu, delete banner) and grouped `DashboardCard`/`AdminCard` into single VoiceOver elements.

## Known Limitations
- **Dynamic Type isn't supported** — text uses fixed `.system(size:)` points throughout rather than scalable `Font` styles, so the UI won't grow with the system's text-size setting. Retrofitting ~80 files' worth of typography to `@ScaledMetric`/semantic text styles is a real, sizeable follow-up, not something to bolt on in the last module without risking every screen's carefully-tuned glass-card layouts. Flagging this honestly rather than claiming full accessibility coverage.
- **VoiceOver coverage is targeted, not exhaustive** — every icon-only control found in an audit got a label, but a full accessibility pass (custom rotor support, more granular `accessibilityValue` on sliders/steppers, etc.) wasn't done across all 80+ files.
